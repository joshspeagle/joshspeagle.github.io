Input pipelines, evaluation, checkpoints and multi-host training

Josh Speagle Notes on the Playbook's section on the training pipeline ↗

Part of a series of notes on Google Research's Deep Learning Tuning Playbook. Read what the Playbook is and how these notes work.

Every earlier post in this series quietly assumed that a training run measures what it claims to measure: that the validation error comes from the right examples at comparable points in training, and that the accelerator spends its time on training steps rather than waiting. The Playbook closes its main guide with a section of engineering advice whose job is to keep those assumptions true. At first glance it reads like a list of unrelated tips, but I think most of the items share a theme, because each one describes a way a pipeline can produce misleading numbers without ever raising an error. In this final post we'll start with a few smoke tests of my own, then follow the Playbook through input throughput, the schedule and sample for periodic evaluation, checkpoint selection and experiment tracking, and finish with the subtler problems of batch norm across devices and multi-host training.

Smoke tests before the first sweep

My addition This section goes beyond the Playbook, whose pipeline guidance does not cover it.

The Playbook's list begins with input performance, but I'd put a more basic question first: is the pipeline wired correctly at all? Speed only matters once the answer is yes, because a wiring bug silently wastes every trial that runs on top of it. The three checks I use, shown in , come from Andrej Karpathy's 2019 blog post A Recipe for Training Neural Networks , and each needs only a short run with no tuning.

Notice that none of these checks measures speed. A pipeline can pass all three and still leave the accelerator idle for half of every step, and that failure is where the Playbook's own list begins.

Where does the accelerator wait?

Suppose a training step takes 100 ms of accelerator time, yet the job runs at about four steps per second instead of ten. Where did the rest of the time go? Usually into producing the next batch: reading files, decoding and augmenting examples, and copying them to the device. A pipeline in this state is input-bound, meaning its speed is set by how fast the host produces examples while the accelerator idles in between. The Playbook is candid that there is no universal fix.

The Playbook Optimizing the input pipeline ↗

The causes and interventions of input-bound pipelines are highly task-dependent; use a profiler and look out for common issues.

A profiler answers the question directly by recording a timeline of what the host and the accelerator are each doing. The Playbook points to Perfetto for JAX and to the TensorFlow profiler, and PyTorch users have torch.profiler. To build intuition for what such a trace shows, I made the simplified timeline in , where one input worker on the host reads and preprocesses each batch and the accelerator then runs the training step on it.

What the toy makes clear is that every stall comes down to one comparison, between how long the host takes to produce a batch and how long the accelerator takes to consume it. The three common causes the Playbook lists each tip that balance in a different way, and each appears as a setting in .

  • Data far from the training process. Reading training data over a network adds I/O latency to every batch. In the toy this is the network-storage setting, where the read segment dominates.
  • Expensive online preprocessing. Decoding and augmenting on the fly can cost more than the training step itself, so the Playbook suggests doing such preprocessing once, offline, and saving the result.
  • Unintentional synchronization barriers. A call that makes the host wait for the device can interfere with prefetching. The Playbook's example is synchronizing metrics between the device and the host in CommonLoopUtils.

The suggested remedies map onto the same picture. Prefetching (for example tf.data.Dataset.prefetch) lets the host prepare upcoming batches while the accelerator computes, which hides input work as long as it is shorter than a step. Stripping unused features and metadata from each example as early in the pipeline as possible shortens the work per batch. Running more jobs that generate examples (for example with the tf.data service) raises the rate at which batches arrive, which is the two-worker setting in the toy. The authors also note that broader engineering concerns, such as keeping the data's disk footprint small, can justify accepting a slower input pipeline.

Before opening a profiler at all, I find one cheap comparison useful (this is my suggestion, not the Playbook's). We feed the training step a batch that already sits in device memory, repeat it for a few hundred steps, and compare the steps per second against the real input pipeline. A large gap tells us the input pipeline is the bottleneck. This is a variant of the throughput check in Part 3, where the Playbook notes that throughput which stops doubling with the batch size before the accelerator saturates points to a bottleneck such as I/O or synchronization between compute nodes.

Evaluating during training

Once batches arrive on time, we can turn to what the pipeline actually measures while it trains. It helps to separate three settings for evaluating a model, which the Playbook distinguishes and sketches. Online evaluation measures the model while it serves predictions in production. Offline evaluation runs it on held-out training, validation and test sets that represent the production environment. Periodic evaluation computes metrics during training as a proxy for the offline evaluation, often on a subset of its data. Tuning lives almost entirely in the third setting, so that is where most of the pitfalls are.

Periodic evaluations serve three purposes in the Playbook's workflow: monitoring training as it happens, supporting retrospective checkpoint selection, and letting us examine the training curves after the run ends. The simplest setup alternates training and evaluation on the same machine, and there the Playbook recommends an evaluation batch size at least as large as the training batch size, because evaluation keeps no activations for a backward pass and so needs less memory per example.

Step intervals, not time intervals

The next decision is when to evaluate. A timer is the easiest schedule to write ("evaluate every ten minutes"), and it has the appeal of making the cost of evaluation predictable. The Playbook nonetheless argues against it.

The Playbook Setting up periodic evaluations ↗

Periodic evaluations should be done at regular step intervals, not time intervals. Evaluating based on time intervals can make it harder to interpret the training curves, especially when training may suffer from preemptions of the training jobs, network latency issues, etc.

To see why the choice matters, I built , which replays one simulated run under both schedules. The job trains at 10 steps per second, slows to 3 steps per second for 600 s of network contention, and is later preempted and restarted from its last checkpoint.

The underlying problem is that a timer spaces evaluations evenly in time and therefore unevenly in steps. The slowdown's stretch of training gets more than three times the usual density of points, and the stretch repeated after the restart is evaluated twice at offset steps, so the line in panel (b) doubles back on itself. Neither feature tells us anything about the model; both are a record of what the cluster happened to be doing.

More worrying, the uneven density changes which checkpoint wins. The best checkpoint is a minimum over noisy evaluations, and a stretch with more evaluations offers more chances for a low noisy value, an order-statistics effect we will return to when we discuss checkpoints. In the run shown, the timer selects step 10,075 from inside the slowdown, while the step schedule selects step 6,500, close to where the noise-free curve is lowest. If two trials hit slowdowns at different times, they are compared on unequal terms. On a step schedule, by contrast, every trial is evaluated at the same steps, so we can overlay curves point by point and every trial gets the same number of chances.

Periodic patterns in validation metrics

Step intervals have a second, less obvious benefit that the Playbook points out. When the training, validation and test split is shuffled, periodicity in the validation or test metrics can indicate an implementation bug, such as test data that overlaps the training data or training data that is not properly shuffled, and regular step intervals make such patterns easier to catch. The Playbook doesn't spell out why, but I read it this way: an epoch is a fixed number of steps, so a pattern tied to the order of the training data repeats every fixed number of step-scheduled evaluations, while a timer smears it across uneven intervals.

Partial batches and saved predictions

A smaller detail can bias the evaluation itself. When the size of the evaluation set is not divisible by the batch size, the final batch is partial, and implementations usually pad it to full size. The Playbook asks that the padded examples be weighted correctly so they do not bias the loss, and notes that they can often simply be given a weight of zero ().

While we are inside the evaluation loop, the Playbook also recommends saving enough information at each evaluation to support offline analysis, ideally the predictions on a selection of individual examples, since these are invaluable for debugging. Artifacts such as TensorFlow SavedModels make ad hoc inspection easy after the evaluation jobs finish.

Choosing the evaluation sample

So far we have asked when to evaluate; the other half of the question is what to evaluate on. A periodic evaluation job often cannot compute metrics on the full offline evaluation set in a reasonable time, which in the Playbook's experience frequently makes a sample for periodic evaluation necessary. Choosing that sample is a small exercise in survey design, and the Playbook lists four considerations.

  • No skew. Performance on the sample should match performance on the whole offline evaluation set.
  • Size. The sample should be small enough to evaluate in full without trouble, yet large enough to measure improvements to the model accurately, so that they are not overwhelmed by label noise.
  • Repeated use. It should be large enough to support many evaluations across trials in sequence without adaptively fitting the validation set in a way that fails to generalize to a held-out test set, although the Playbook adds that this is rarely a practical concern. (For the theory of reusing a holdout set, see Dwork et al. (2015).)
  • Imbalanced classes. Performance on rare classes will often be noisy, so for a class with few examples the Playbook suggests logging the number of examples predicted correctly.

The authors illustrate the last point with a pointed question: ".05 sensitivity improvement sounds exciting, but was it just one more example correct?" With 20 validation examples in a class, the answer is yes ().

How large a sample resolves a given improvement

The Playbook leaves "large enough" qualitative, so here is a rough guide of my own based on the binomial distribution. An accuracy $p$ measured on $n$ independent examples has standard error

$$\mathrm{SE} = \sqrt{\frac{p\,(1-p)}{n}}.$$

For $p = 0.9$, the standard error is about 0.009 on 1,000 examples and 0.003 on 10,000, and a difference between two checkpoints smaller than about twice the standard error is hard to separate from sampling noise. Comparing two models on the same examples is less noisy than this suggests, because the examples that both get right or both get wrong cancel out of the difference. For a rare class, $n$ is the number of examples in that class, which is why its metrics move in steps of $1/n$.

Checkpoints and retrospective selection

The Playbook Saving checkpoints ↗

Run training for a fixed number of steps and retrospectively choose the best checkpoint from the run.

Most frameworks already save the model's state to disk periodically, mainly so that a training job survives interruptions. The Playbook's point is that those same checkpoints can do more work, because the best one is often not the last, particularly once validation performance stops improving and fluctuates about a value. Its recommendation is for the pipeline to keep the N best checkpoints seen so far (a checkpoint buffer) and choose the best of them at the end of training, a procedure it calls retrospective optimal checkpoint selection. Since each trial runs for a pre-specified number of steps and the best checkpoints are kept along the way, prospective early stopping (ending a run when validation performance stalls) is usually unnecessary.

Retrospective selection is also where the lesson of comes back. A trial's result is a minimum over noisy evaluations, so it depends on how many evaluations the trial received, which is the same effect as taking the best of many trials in Part 4. We can't remove that bias, but a fixed step interval at least gives every trial in a study the same number of evaluations at the same steps, so the bias is roughly equal across trials and largely drops out of the comparison.

How much lower does the minimum of more evaluations fall?

This calculation is my addition rather than the Playbook's. If a stretch of training has a level validation error $\bar V$ and each evaluation adds independent noise with standard deviation $\sigma$, the minimum of $M$ evaluations falls below $\bar V$ by an amount that grows with $M$. For large $M$ the expected shortfall approaches $\sigma\sqrt{2\ln M}$, and for $M$ between 5 and 25 it is about $1.2\sigma$ to $2.0\sigma$ (the factors $m_K$ in the selection-bias aside of Part 6). In the slowdown holds 24 timer evaluations against 8 step-scheduled ones, enough to move the selected checkpoint.

Experiment tracking

The Playbook Setting up experiment tracking ↗

When tracking different experiments, make sure to note a number of essentials like the best performance of a checkpoint in the study, and a short description of the study.

Everything so far concerns a single trial, but over weeks of tuning the results that matter end up spread across dozens of studies, and a careful evaluation is of little use if nobody can find it later. The Playbook's authors keep their experiment tracking results in a spreadsheet with the six columns in . They are not attached to the tool, asking only for a system that captures at least this information and is convenient for the people using it, and they close with a blunt warning: "Untracked experiments might as well not exist."

Hosted experiment trackers record configurations and curves automatically, which takes care of the config, trial and performance columns. The description and reproduction columns are different, because someone still has to write them while the study is fresh, and a returning reader has no other way to recover what they record.

Batch norm across devices

The Playbook Batch normalization implementation details ↗

Nowadays batch norm can often be replaced with LayerNorm, but in cases where it cannot, there are tricky details when changing the batch size or number of hosts.

Like the multi-host issues in the next section, these details produce bugs that are hard to spot, because the code runs and the numbers look plausible. Recall that batch norm normalizes each feature (a channel, in a convolutional network) using the mean and variance of that feature over a group of $n$ examples. For an activation $z_i$ of example $i$,

$$\hat{z}_i = \frac{z_i - \htmlClass{math-col-model}{\bar{z}}}{\sqrt{\htmlClass{math-col-model}{s^2} + \epsilon}}, \qquad \htmlClass{math-col-model}{\bar{z}} = \frac{1}{\htmlClass{math-col-third}{n}}\sum_{j=1}^{\htmlClass{math-col-third}{n}} z_j,$$

where $s^2$ is the variance over the same $n$ examples and $\epsilon$ is a small constant. At test time the layer instead uses exponential moving averages (EMAs) of these statistics collected during training. The subtlety the Playbook raises first is that with several devices, each holding part of the batch, the statistics differ from device to device unless they are explicitly synchronized. Without synchronization, $n$ equals the per-device batch size, $B/D$ for a global batch size $B$ split over $D$ devices, which means that changing either the batch size or the device count also changes $n$.

Why should we care about $n$? Because it changes the objective itself. Goyal et al. (2017) make this explicit: "if the per-worker minibatch sample size $n$ is changed, it changes the underlying loss function $L$ that is optimized", because the statistics "computed by BN with different $n$ exhibit different levels of random variation". For that reason they kept $n = 32$ per worker throughout their large-batch ImageNet runs. compares what each normalization scheme averages over.

If $n$ matters, which value should we pick? The Playbook reports that anecdotally, mostly on ImageNet, computing the statistics over only about 64 examples works better in practice, and it points to ghost batch norm, introduced by Hoffer et al. (2017), which computes the statistics over small virtual batches inside a large batch. We should keep the provenance of the numbers straight here: the 64 is the Playbook authors' anecdote, while Hoffer et al. used ghost batches of 128, mostly on CIFAR. Whatever the value, decoupling the total batch size from the number of examples in the statistics is particularly useful when comparing batch sizes, which is where Part 3 ran into the same issue.

Two implementation details deserve attention, one about per-device batch sizes and one about the moving averages used at test time.

  • Per-device batches larger than the ghost batch. Ghost batch norm implementations do not always handle a per-device batch size larger than the virtual batch size. In that case each device has to subsample its batch to compute statistics over the intended number of examples.
  • The EMAs used at test time. The moving averages are linear combinations of training statistics, so synchronizing them across devices before they are saved in a checkpoint is enough. Some common implementations never synchronize them and save the EMA from the first device.

All of this bookkeeping explains why the Playbook suggests replacing batch norm where possible. Layer norm normalizes each example over its own features, and group norm over groups of channels within an example. Since neither uses other examples, neither depends on the batch size or the number of devices, and the whole problem disappears.

Multi-host pipelines

The Playbook Considerations for multi-host pipelines ↗

For logging, evals, RNGs, checkpointing, and data sharding, multi-host training can make it very easy to introduce bugs!

A multi-host pipeline runs one training job across several machines, each driving its own accelerators. In the usual setup every host runs the same program, and that symmetry is the source of the trouble: anything that should happen only once, or should differ between hosts, has to be arranged explicitly. I find it easiest to read the Playbook's four rules as a statement of what should be shared across hosts and what should differ, which is how lays them out.

  • Log and checkpoint on one host. Otherwise every host writes the same files, and the copies overwrite or duplicate one another.
  • Synchronize batch norm statistics before evaluation or checkpointing. The saved model then reflects the statistics of all hosts, which is the multi-host form of the EMA point in the batch norm section.
  • Mark each RNG seed by its role. The Playbook calls it critical to use seeds that are the same across hosts for model initialization and seeds that differ across hosts for data shuffling and preprocessing. The reasoning is left implicit, but I read it as guarding against two opposite failures: different initialization seeds start the replicas from different weights, while identical data seeds can give hosts identical batches when they read the same files.
  • Shard data files across hosts. The Playbook recommends this for performance.

In practice

Taken together, the advice in this post is easiest to use if you sort it by when you act on it rather than by topic. Items marked as my addition are not in the Playbook.

1

Before the first sweep

  1. Run the smoke tests on a new pipeline: look at a batch, check the step-0 loss, overfit one batch. My addition
  2. Profile the input pipeline. Compare steps per second against a cached batch, prefetch, and add input workers if the host cannot keep up.
  3. On several hosts, log and checkpoint on host 0, mark each seed by its role, and shard the data files.
2

While each trial trains

  1. Evaluate every fixed number of steps, with an evaluation batch at least as large as the training batch.
  2. Give padded examples zero weight and save predictions on a selection of examples.
  3. Keep the N best checkpoints, with batch norm statistics synchronized before each save.
3

After each study

  1. Select the best checkpoint retrospectively as the trial's result.
  2. Add a row to the tracking sheet: name, config link, description, trials, best validation performance, reproduction notes.
  3. Check the evaluation sample against the full offline set, and read rare-class results as counts.
