Choosing the batch size

Josh Speagle Notes on the Playbook's section on choosing the batch size ↗

Part of a series of notes on Google Research's Deep Learning Tuning Playbook. Read what the Playbook is and how these notes work.

The batch size is one of the first settings you fix on a new project, and it is tempting to treat it like the learning rate, trying a few values and keeping whichever validates best. The Playbook argues against this. Once the other hyperparameters are retuned and the run is long enough, the batch size changes how quickly you reach a result, not how good that result can be. The useful questions are which batch sizes your hardware can run, how much faster each one trains, and what each one costs.

What batch size controls

The Playbook's summary of the topic is two sentences long. The batch size "governs the training speed and shouldn't be used to directly tune the validation set performance", and "often, the ideal batch size will be the largest batch size supported by the available hardware" . The argument behind the first sentence has a condition attached. If the learning rate, the regularization hyperparameters and the number of training steps are retuned for each batch size, the Playbook expects the same final performance from any batch size.

The evidence comes mostly from Shallue et al. , who retuned every run at every batch size on workloads spanning several model families, optimizers and datasets. Their abstract states: "We find no evidence that larger batch sizes degrade out-of-sample performance." The Playbook's FAQ words its conclusion with the same care, saying there is "no convincing evidence that the batch size affects the maximum achievable validation performance". Both are reports of an effect that was not found on the workloads tested. Neither is a proof that no such effect exists.

Many people have seen validation error get worse after raising the batch size, and the Playbook agrees that "changing the batch size without changing any other details of the training pipeline will often affect the validation set performance". The number of epochs and the learning rate usually stay fixed by accident:

  • The number of epochs. A script that trains for a fixed number of epochs (passes over the training set) processes a fixed number of examples $E$, so the number of steps $S = E/B$ falls as the batch size $B$ grows. Doubling the batch size halves the number of weight updates. Hoffer et al. found that the large-batch gap in their experiments "stems from the relatively small number of updates rather than the batch size", and closed it by training for proportionally more updates with an adjusted learning rate.
  • The learning rate and regularization. A learning rate tuned at $B = 64$ is usually a poor choice at $B = 2{,}048$, because averaging more examples produces a less noisy gradient and supports larger steps (see steps needed). The Playbook names the optimizer hyperparameters (learning rate, momentum) and the regularization hyperparameters as the ones that interact most strongly with the batch size.

If the batch size mainly sets speed, the reasons to care about it are practical ones. In the Playbook's account, faster training lets you tune hyperparameters more thoroughly in a fixed amount of time, and it shortens the development cycle so that new ideas get tested more often. Training time is the product of step latency (seconds per step) and step count:

$$T(B) \;=\; \htmlClass{math-col-third}{t_{\text{step}}(B)} \times \htmlClass{math-col-fourth}{S(B)}.$$

Each factor depends on the batch size for a different reason. Step latency depends on the hardware. Step count depends on the statistics of the gradient.

Time per step on real hardware

The first practical question on a new workload is which batch sizes fit on the accelerator (a GPU or TPU) and how long a step takes at each. Memory and parallelism decide the answer.

  • Memory sets an upper limit. During training the accelerator holds the weights, their gradients and the optimizer state (Adam keeps two extra values per weight), and none of these depend on the batch size. It also holds the activations of every layer for every example in the batch, because the backward pass needs them to compute the gradient. Activation memory therefore grows in proportion to $B$, and above some batch size the run fails with an out-of-memory error. The Playbook calls accelerator memory "usually" the limiting factor, and warns that the limit "can be difficult to calculate ... without running, or at least compiling, the full training program".
  • Parallel hardware saturates. The accelerator processes the examples of a batch in parallel. At small batch sizes some of its arithmetic units sit idle, so a batch twice as large takes about the same time per step. Once the units are busy, a batch twice as large takes about twice as long. Training throughput (examples processed per second, $B / t_{\text{step}}$) therefore doubles with each doubling at first and then reaches a throughput plateau. The Playbook states the first half directly: "When the accelerators aren't yet saturated, if the batch size doubles, the training throughput should also double (or at least nearly double)."

Because the memory limit is hard to predict, the Playbook recommends measuring it with a doubling procedure. Run training for a small number of steps at increasing powers of two until one run exceeds memory, and record the throughput of each run. Two outcomes call for action:

  • Throughput does not double below saturation. The pipeline then has a bottleneck "such as I/O or synchronization between compute nodes", which the Playbook says "may be worth diagnosing and correcting before proceeding".
  • Throughput stops rising. The Playbook advises considering only batch sizes up to that point, "even if a larger batch size is supported by the hardware", because "all benefits of using a larger batch size assume the training throughput increases".

With the saturating accelerator, every doubling up to $B =$ 1,024 raised throughput by at least 14%, and the next doubling added 1%. With the preset, throughput stops near 2,000 examples per second from $B =$ 256, well below the accelerator's peak. That early plateau is the expected pattern for a data loader that cannot keep the accelerator busy.

Gradient accumulation offers a way past the memory limit. It sums the gradients of several micro-batches and updates the weights once. The Playbook advises against it in applied work, because it "simulates a larger batch size than the hardware can support and therefore does not provide any throughput benefits". The micro-batches run one after another, so the time per step grows in proportion to the accumulated batch size. The Playbook also notes that the measurements "may need to be repeated every time the model or optimizer is changed", since a different architecture can change what fits in memory.

Steps needed fall, then level off

The second factor is the number of steps needed to reach a fixed validation goal, with the hyperparameters retuned at each batch size. Shallue et al. measured this "steps to result" on every workload in their study and found the same shape each time. There is "an initial period of perfect scaling ... where the steps needed to achieve the error goal halves for each doubling of the batch size", then "a region of diminishing returns", and finally "a region of maximal data parallelism where additional parallelism provides no benefit whatsoever". They "never saw the number of steps to reach a goal validation error increase when the batch size was increased". The Playbook repeats this as a rule (more steps are "never" needed), but it remains an empirical regularity. The Playbook calls the halving regime perfect scaling.

Gradient noise explains the shape. Each step uses an estimate of the full-data gradient computed from $B$ examples. The error of that estimate has a variance proportional to $1/B$, because averaging $B$ independent per-example gradients divides their variance by $B$. While noise dominates, the optimizer must take small steps, and a step at double the batch size is nearly as good as two steps at the smaller batch size. Once the estimate is accurate, adding examples improves it little, and the curvature of the loss limits the step size instead. McCandlish et al. made this argument quantitative.

Turning progress per step into a step count gives McCandlish et al.'s model of the steps $S$ and training examples $E$ needed to reach a goal at batch size $B$ (their Eq. 2.11, solved at fixed $B$):

$$\begin{aligned} \htmlClass{math-col-fourth}{S(B)} &= S_{\min}\left(1 + \frac{\htmlClass{math-col-model}{B_{\text{crit}}}}{B}\right), \\[4pt] E(B) = B\,S(B) &= E_{\min}\left(1 + \frac{B}{\htmlClass{math-col-model}{B_{\text{crit}}}}\right). \end{aligned}$$

Here $S_{\min}$ is the number of steps a very large batch needs, $E_{\min}$ is the number of examples a very small batch needs, and $B_{\text{crit}} = E_{\min}/S_{\min}$ is the critical batch size. McCandlish et al. fit $B_{\text{crit}}$ to measured runs, and their noise argument predicts it to be close to the gradient noise scale averaged over training. At $B = B_{\text{crit}}$ a run takes twice the minimum number of steps and twice the minimum number of examples, which they call "a natural compromise between time and compute".

Where the noise scale comes from

Let $G$ be the full-data gradient, $H$ the Hessian (the matrix of second derivatives of the loss), and $\Sigma$ the covariance of a single example's gradient. A step of size $\eta$ along a mini-batch estimate changes the loss, to second order and on average, by

$$\Delta L(\eta) \approx -\eta\,|G|^2 + \tfrac{1}{2}\,\eta^2\left(G^{\top} H G + \frac{\operatorname{tr}(H\Sigma)}{B}\right).$$

Minimizing over $\eta$ gives McCandlish et al.'s Eqs. 2.6 and 2.7:

$$\eta^{\star}(B) = \frac{\eta_{\max}}{1 + B_{\text{noise}}/B},$$ $$\Delta L^{\star}(B) = \frac{\Delta L_{\max}}{1 + B_{\text{noise}}/B},$$

where $\eta_{\max} = |G|^2 / G^{\top} H G$ is the best step on the exact gradient and $B_{\text{noise}} = \operatorname{tr}(H\Sigma)/G^{\top} H G$ is the noise scale (their Eq. 2.8). If the Hessian is close to a multiple of the identity, this reduces to $B_{\text{simple}} = \operatorname{tr}(\Sigma)/|G|^2$ (their Eq. 2.9), which can be estimated during training. The argument is local to one step and assumes a tuned learning rate. The authors note that it "says nothing about generalization".

Different papers attach the phrase "critical batch size" to different points on this curve (). The tolerances below are my algebra on McCandlish et al.'s curve:

  • The Playbook uses it for the end of perfect scaling: "Perfect scaling holds for all batch sizes up to a critical batch size, beyond which one achieves diminishing returns." On a smooth curve that end needs a tolerance. Zhang et al. (2024) define the critical batch size as the point where the steps needed exceed perfect scaling by 20%. On McCandlish et al.'s curve that point is $B_{\text{crit}}/5$, because the ratio of $S(B)$ to the perfect-scaling line $S_{\min} B_{\text{crit}}/B$ is $1 + B/B_{\text{crit}}$.
  • McCandlish et al. place $B_{\text{crit}}$ in the middle of the bend. A doubling there saves 25% of the steps.
  • Shallue et al. call the point where steps stop falling the "maximum useful batch size". If "stop" means within 10% of the floor $S_{\min}$, it lies at $10\,B_{\text{crit}}$.

The rest of this post uses $B_{\text{crit}}$ (and $B_{\text{noise}}$ for the single-step gradient noise scale) in McCandlish et al.'s sense, because it comes with an equation, $B_{\text{sat}}$ for the hardware saturation batch size, and "end of perfect scaling" for the Playbook's point.

The critical batch size depends on the workload and on the goal. The Playbook says the time-minimizing batch size "depends on the dataset, model, and optimizer", and calls it "an open problem how to calculate it other than finding it experimentally for every new problem". McCandlish et al. found that the critical batch size "typically increases by an order of magnitude or more over the course of training", so a harder goal has a larger one, and their values ranged from about 20 for a small autoencoder to over 10 million for a Dota 2 agent. Zhang et al. (2019) found that momentum and preconditioned optimizers such as Adam raise it. For language-model pre-training, Zhang et al. (2024) found it grows mainly with the amount of training data (roughly as $D^{0.47}$) and only weakly with model size at fixed data.

Wall-clock time is the product

With step latency and step count known, the training time $T(B) = t_{\text{step}}(B) \times S(B)$ follows. On log axes a product becomes a sum, so the curve of $\log T$ is the vertical sum of the curves of $\log t_{\text{step}}$ and $\log S$. Below saturation the time per step is flat, and training time falls as fast as the step count. Above saturation the time per step doubles with each doubling of $B$, while the step count at best halves, so training time can at best stay level. The fastest batch size therefore sits near the saturation batch size or the end of perfect scaling, whichever is smaller.

The presets show the two orders in which perfect scaling and saturation can end:

  • Perfect scaling ends well past saturation (, ending at 16,384). Step latency and step count cancel over a wide range, and every batch size from 704 to 5,953 (a range of 8.5×) finishes within 5% of the fastest time. Any batch size that saturates the accelerator is close to optimal.
  • Perfect scaling ends before saturation (, ending at 64, so $B_{\text{crit}} =$ 320). The step count flattens while the time per step is still constant, and batches above saturation slow training down. The minimum is at $B =$ 466, and $B = 4{,}096$ takes 349% longer.

The Playbook's rule of thumb rests on the first case. It treats the time per step as roughly constant across feasible batch sizes, which holds "when there is no overhead from parallel computations and all training bottlenecks have been diagnosed and corrected". It then observes that "often, the largest batch size supported by the available hardware will be smaller than the critical batch size", so that "a good rule of thumb (without running any experiments) is to use the largest batch size possible". The second case is the exception, and it occurs in practice. McCandlish et al. measured critical batch sizes in the hundreds for small image tasks. The Playbook's closing point covers both cases: "There is no point in using a larger batch size if it ends up increasing the training time."

Epoch budgets, step budgets and cost

A comparison of batch sizes needs a training length for each run, and the length can be fixed in examples (an epoch budget) or in steps (a step budget). The choice decides which batch size looks best. Under McCandlish et al.'s model the examples needed, $E(B)$, grow with the batch size while the steps needed, $S(B)$, shrink. A fixed epoch budget therefore favors small batches, which use examples efficiently, and a fixed step budget favors large batches, which use steps efficiently. The Playbook's warning follows: "Comparing batch sizes with an epoch budget only probes the perfect scaling regime, even when larger batch sizes might still provide a meaningful speedup by reducing the number of training steps required."

The distinction matters when reading published comparisons. Goyal et al. trained ImageNet ResNets for a fixed 90 epochs at every batch size and found error "stable across a broad range of minibatch sizes, from 64 to 8k, after which it begins to increase". Shallue et al. point out that under an epoch budget a larger batch can match a smaller one only while scaling is perfect. The 8k limit may therefore mark the end of perfect scaling for that workload (my reading).

Resource consumption

The Playbook separates the costs of a larger batch into upfront costs, "e.g. purchasing new hardware or rewriting the training pipeline to implement multi-GPU / multi-TPU training", and usage costs, such as cloud bills, team compute budgets and electricity. For usage it writes the same kind of product as for time:

$$\text{consumption} = (\text{per step}) \times (\text{steps}).$$

A larger batch reduces the number of steps, so the outcome depends on what happens to the consumption per step. The Playbook gives an example of each of the three outcomes.

I draw one consequence from this. On a fixed set of accelerators, usage is measured in device-hours, which are proportional to wall-clock time. On that hardware the batch size that minimizes training time also minimizes cost, and answers both questions. The two goals separate only when a larger batch requires more devices or different ones.

For upfront costs, the Playbook suggests it "might be better to defer increasing the batch size until the project has matured", since multi-host pipelines can introduce bugs. It also notes the opposite pressure: "a large speedup in training time might be very beneficial early in the process when a lot of tuning experiments are needed".

Changing the batch size means retuning

The Playbook is direct about what a change costs: "The optimal values of most hyperparameters are sensitive to the batch size. Therefore, changing the batch size typically requires starting the tuning process all over again." Its advice is to keep this in mind when choosing the batch size at the start of a project, because retuning everything later "might be difficult, time consuming, and expensive".

The learning rate shows why. In McCandlish et al.'s model the best SGD learning rate is $\eta^{\star}(B) = \eta_{\max}/(1 + B_{\text{noise}}/B)$ (their Eq. 2.6). Well below the noise scale it grows in proportion to $B$, and well above it the rate levels off at $\eta_{\max}$ (). Empirical results on how to scale the learning rate differ by optimizer:

  • Linear scaling for momentum SGD. Goyal et al.'s rule is "When the minibatch size is multiplied by k, multiply the learning rate by k." They report that it fails early in training, which they handle with warmup, and beyond a batch size of about 8k on ImageNet. Zhang et al. (2019) found the optimal learning rate of SGD "scales linearly with batch size before it hits the critical batch size".
  • Between square root and linear for Adam. McCandlish et al. found that "for Adam and RMSProp the optimal learning rate initially obeys a power law $\varepsilon(B) \propto B^{\alpha}$ with $\alpha$ between 0.5 and 1.0 depending on the task, then becomes roughly constant" (their $\varepsilon$ is the learning rate and their $\alpha$ an exponent).
  • No reliable rule. Shallue et al. found that the optimal values "did not always follow either a linear or square root scaling heuristic".

A scaling rule therefore gives a good place to center the new search, which still has to be run.

Regularization moves too. The Playbook's FAQ argues that smaller batches add sampling noise that "can have a regularizing effect", so larger batches "may require stronger regularization and/or additional regularization techniques". The papers above are more cautious on this point. Hoffer et al. attribute the large-batch gap to the number of updates. Shallue et al. note that small-batch noise may regularize, and that "other regularization techniques, such as label smoothing, can replace this effect".

Batch norm couples the batch size to the model

Batch normalization normalizes each layer's activations with a mean and variance computed over the examples in the batch, so in a model that uses it the batch size changes the computation itself. According to Goyal et al., changing the number of examples $n$ used for these statistics "changes the underlying loss function L that is optimized", because the statistics "computed by BN with different n exhibit different levels of random variation". They fixed $n = 32$ examples per worker.

The Playbook's advice is that batch norm "should use a different batch size than the gradient computation to compute statistics". Ghost batch norm, introduced by Hoffer et al., does this by normalizing small virtual batches inside a large one (they used ghost batches of 128). The Playbook adds anecdotal reports that statistics over about 64 examples work better in practice, and notes that separating the two sizes "is particularly useful for batch size comparisons". It also notes that batch norm "can often be replaced with LayerNorm", which does not depend on the batch. Part 9 covers the implementation details for multiple devices.

In practice

The Playbook's advice on batch size condenses into a short procedure. Steps 1 to 4 come from its section on feasible batch sizes and throughput ↗ and on minimizing training time ↗. Steps 5 and 6 come from its sections on retuning ↗ and resource consumption ↗.

  1. Measure throughput by doubling

    Run a few steps at batch sizes 8, 16, 32, and so on until a run fails for memory. Record examples per second for each.

  2. Fix bottlenecks before choosing

    If throughput does not nearly double while the accelerator is unsaturated, look for an input or synchronization bottleneck first.

  3. Keep the batch sizes that raise throughput

    Drop batch sizes past the throughput plateau, even if they fit. Avoid gradient accumulation, which adds no throughput.

  4. Default to the largest of them

    Without experiments, use the largest batch size that still raises throughput. To check it, compare candidates by steps to a fixed goal under a step budget, retuned at each batch size.

  5. Retune whenever the batch size changes

    Retune the learning rate, momentum and regularization. Use a scaling rule only to center the search. With batch norm, keep the statistics size fixed.

  6. Weigh cost only when hardware changes

    On fixed hardware the fastest batch size is also the cheapest. When a larger batch needs more or better devices, compare consumption per step against the steps saved.
