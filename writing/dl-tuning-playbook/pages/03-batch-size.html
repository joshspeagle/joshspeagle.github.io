Choosing the batch size

Josh Speagle Notes on the Playbook's section on choosing the batch size ↗

Part of a series of notes on Google Research's Deep Learning Tuning Playbook. Read what the Playbook is and how these notes work.

The batch size is one of the first numbers fixed on a new project, tempting many teams to sweep it like a learning rate and pick whichever validates best. The Playbook rejects that framing: once other hyperparameters adjust and training runs long enough, batch size governs how fast you reach a result rather than its ceiling. That turns the question into hardware saturation, step count, and compute cost. Here I trace that argument from the invariance evidence, through latency and gradient noise, into budgets and retuning.

In brief
  • Optimize speed, not peak score: With retuned optimizer settings and enough steps, larger batches match small-batch validation quality (What the batch size controls).
  • Measure hardware limits by doubling: Sweep powers of two until memory fails, fix pipeline bottlenecks first, and drop sizes past the throughput plateau (Time per step).
  • Know saturation versus noise scale: Fastest training sits near saturation or critical batch size; modern runs hit high token batches using bf16 and accumulation across parallel shards (Wall-clock time).
  • Retune after every batch change: Scaling rules only center a fresh sweep, and BatchNorm needs a decoupled statistics size (Retuning).

What the batch size controls

The Playbook states its position in two sentences. Batch size "governs the training speed and shouldn't be used to directly tune the validation set performance", and "often, the ideal batch size will be the largest batch size supported by the available hardware" [1]. That claim rests on a vital condition: Godbole et al. expect the same final performance from any batch size only when learning rate, regularization, and training steps are retuned for each candidate.

Most of that evidence traces to Shallue et al. [6], who retuned every batch size across models, optimizers, and datasets. They write: "We find no evidence that larger batch sizes degrade out-of-sample performance." The Playbook's FAQ reports "no convincing evidence that the batch size affects the maximum achievable validation performance." Both state an empirical absence across tested benchmarks rather than a universal theorem.

Wait: that claim clashes with common experience whenever raising the batch size hurts validation error. The Playbook agrees that "changing the batch size without changing any other details of the training pipeline will often affect the validation set performance," usually because two settings stay fixed by mistake:

  • The number of epochs. Scripts configured for fixed epochs (dataset passes) keep total examples $E$ constant. As batch size $B$ grows, update steps $S = E/B$ fall in proportion, halving optimization steps per doubling. Hoffer et al. [3] showed that this large-batch gap "stems from the relatively small number of updates rather than the batch size," closing it by matching update counts and scaling the learning rate.
  • The learning rate and regularization. A learning rate tuned at $B = 64$ rarely suits $B = 2{,}048$, because averaging more examples stabilizes the gradient enough for larger steps (Steps needed explains why). The Playbook highlights optimizer and regularization settings as tightly coupled to batch size.

If batch size primarily controls speed, its payoff is practical. As the Playbook notes, faster training fits deeper sweeps into a fixed wall-clock window and speeds up iteration cycles. To reason cleanly about speed, write training time as step latency times step count:

$$T(B) \;=\; \htmlClass{math-col-third}{t_{\text{step}}(B)} \times \htmlClass{math-col-fourth}{S(B)}.$$

This split helps because hardware fixes step latency while gradient statistics govern step count. Next you examine both factors in turn.

Time per step on real hardware

Before optimizing speed on a workload, you must measure which batch sizes fit on your accelerator (GPU or TPU) and how fast each step runs. Two hardware ceilings set these bounds: memory and parallelism.

  • Memory sets an upper limit. Accelerators hold static tensors (model weights, gradients, and optimizer states, where AdamW stores two fp32 moments per weight) regardless of batch size. Under modern mixed precision, forward and backward passes typically compute in bf16 while optimizer states stay in fp32, halving activation memory per example relative to full precision. Because activation memory still scales linearly with $B$, exceeding device RAM triggers an out-of-memory failure. As the Playbook notes, exact limits remain "difficult to calculate ... without running, or at least compiling, the full training program."
  • Parallel hardware saturates. Accelerators vectorize across examples in a batch, leaving compute units idle at tiny batch sizes so doubling $B$ barely lengthens step time. Once hardware saturates, doubling $B$ doubles step latency. Training throughput ($B / t_{\text{step}}$ examples per second) therefore doubles initially before flattening at peak hardware bandwidth. In the Playbook's words: "When the accelerators aren't yet saturated, if the batch size doubles, the training throughput should also double (or at least nearly double)."

Because memory limits vary across compilers and kernels, the Playbook recommends finding them empirically via a doubling procedure: benchmark brief runs across powers of two until one fails for memory, logging throughput throughout. Two outcomes require immediate fixes:

  • Throughput fails to double before saturation. This signals a pipeline bottleneck, "such as I/O or synchronization between compute nodes," which the authors advise diagnosing before moving on.
  • Throughput stops rising. Keep only batch sizes up to peak saturation, "even if a larger batch size is supported by the hardware," since throughput gains drive batch-size speedups.

On the saturating accelerator, doublings up to $B =$ 1,024 raised throughput by at least 14% while the next added only 1%, stopping there. With , throughput stalls at 2,000 examples/s from $B =$ 256 upward. An early flat ceiling like that tells you the data loader cannot feed the accelerator.

What if you need effective batches past single-device memory? Gradient accumulation sums gradients across sequential micro-batches before stepping the optimizer. On fixed hardware, the Playbook warns against it because sequential passes "simulate a larger batch size than the hardware can support and therefore does not provide any throughput benefits." Modern large-scale pre-training uses accumulation for a different reason: Zhang et al. (2024) [10] show that critical batch size grows with token budget $D$, so multi-million-token optimizer steps often exceed per-replica activation memory even across parallel shards. Accumulation lets you match that target optimization batch size cleanly, yet speedup still requires adding parallel accelerators rather than accumulating longer on the same device. Finally, re-benchmark whenever model, precision, or optimizer states change.

Steps needed fall, then level off

The second factor is how many steps are needed to hit a fixed validation score once hyperparameters adjust. Shallue et al. [6] mapped this "steps to result" curve across diverse tasks, finding three universal regimes: "an initial period of perfect scaling ... where the steps needed to achieve the error goal halves for each doubling of the batch size," a bend of "diminishing returns," and "maximal data parallelism where additional parallelism provides no benefit whatsoever." They "never saw the number of steps to reach a goal validation error increase when the batch size was increased." The Playbook calls that halving region perfect scaling and takes monotonicity as a rule of thumb, while remembering it remains an empirical regularity rather than a guarantee.

Why does the curve bend? Every step uses a stochastic gradient estimated from $B$ examples, whose estimation variance scales as $1/B$. While sampling noise dominates, taking one step with twice the batch size buys nearly as much progress as two smaller steps. Once the gradient estimate sharpens past noise, adding more examples stops shrinking curvature error and step count hits a floor. McCandlish et al. [5] turn that variance argument into the quantitative model I use throughout the rest of this post.

Turning single-step progress into a total run length leads to McCandlish et al.'s curve linking steps $S$ and examples $E$ to reach a fixed target at batch size $B$ (their Eq. 2.11):

$$\begin{aligned} \htmlClass{math-col-fourth}{S(B)} &= S_{\min}\left(1 + \frac{\htmlClass{math-col-model}{B_{\text{crit}}}}{B}\right), \\[4pt] E(B) = B\,S(B) &= E_{\min}\left(1 + \frac{B}{\htmlClass{math-col-model}{B_{\text{crit}}}}\right). \end{aligned}$$

Here $S_{\min}$ is the asymptotic large-batch step floor, $E_{\min}$ is the small-batch data floor, and $B_{\text{crit}} = E_{\min}/S_{\min}$ is the critical batch size. Larger $B$ cuts step counts yet increases total examples trained. At $B = B_{\text{crit}}$, both steps and examples sit at twice their theoretical minimums, a point McCandlish et al. call "a natural compromise between time and compute."

Where the noise scale comes from

The second-order derivation is brief. Let $G$ be the full-data gradient, $H$ the Hessian, and $\Sigma$ the per-example gradient covariance. Averaging over a mini-batch of size $B$, a step $\eta$ moves the expected loss by

$$\Delta L(\eta) \approx -\eta\,|G|^2 + \tfrac{1}{2}\,\eta^2\left(G^{\top} H G + \frac{\operatorname{tr}(H\Sigma)}{B}\right).$$

Minimizing over $\eta$ recovers McCandlish et al.'s Eqs. 2.6 and 2.7:

$$\eta^{\star}(B) = \frac{\eta_{\max}}{1 + B_{\text{noise}}/B},$$ $$\Delta L^{\star}(B) = \frac{\Delta L_{\max}}{1 + B_{\text{noise}}/B},$$

where $\eta_{\max} = |G|^2 / G^{\top} H G$ and $B_{\text{noise}} = \operatorname{tr}(H\Sigma)/G^{\top} H G$ (their Eq. 2.8). When $H$ is near isotropic, this reduces to $B_{\text{simple}} = \operatorname{tr}(\Sigma)/|G|^2$ (Eq. 2.9), measurable online during training. Remember the derivation's scope: it is local to one quadratic step, assumes an optimal step size, and "says nothing about generalization."

Papers also attach "critical batch size" to different landmarks along the same curve (Figure 5); the numerical boundaries below apply algebra to McCandlish et al.'s curve:

  • The Playbook places it at the end of perfect scaling: "Perfect scaling holds for all batch sizes up to a critical batch size, beyond which one achieves diminishing returns." Pinning that bend on a smooth curve needs a threshold; Zhang et al. (2024) [10] define it where steps exceed perfect scaling by 20%, which falls at $B_{\text{crit}}/5$ on $S(B)$.
  • McCandlish et al. define $B_{\text{crit}}$ at the knee itself, where doubling the batch saves 25% of steps.
  • Shallue et al. name the step-floor transition the "maximum useful batch size." Defining "near the floor" as within 10% of $S_{\min}$ locates it at $10\,B_{\text{crit}}$.

For consistency, I keep $B_{\text{crit}}$ in McCandlish et al.'s sense across this post, writing $B_{\text{noise}}$ for single-step noise scale, $B_{\text{sat}}$ for hardware saturation, and "end of perfect scaling" for the Playbook's landmark.

Under either convention, critical batch size is never a universal constant. The Playbook notes it "depends on the dataset, model, and optimizer," making it "an open problem how to calculate it other than finding it experimentally." McCandlish et al. showed $B_{\text{crit}}$ grows by over an order of magnitude across training as lower losses demand cleaner gradients, spanning roughly 20 on a small autoencoder to over 10 million in RL. Zhang et al. (2019) [9] showed momentum and Adam increase it further; for LLM pre-training, Zhang et al. (2024) [10] found it scales primarily with training tokens $D$ (roughly $D^{0.47}$) rather than parameter count alone.

Wall-clock time is the product of the two

Combining both curves yields $T(B) = t_{\text{step}}(B) \times S(B)$. On log axes the product turns into a sum, adding step latency vertically to step count. Below saturation, step latency stays flat, so total time drops step-for-step with $S(B)$; past saturation, step latency doubles per doubling while steps at best halve, flattening or raising $T(B)$. Fastest training therefore sits near the earlier of hardware saturation or the end of perfect scaling.

What matters is which ceiling arrives first, illustrated by the two presets:

  • Perfect scaling ends past saturation (, ending at 16,384). Step latency and step count trade off smoothly, keeping any batch from 704 to 5,953 (8.5×) within 5% of optimal speed.
  • Perfect scaling ends before saturation (, ending at 64; $B_{\text{crit}} =$ 320). Step count flattens before hardware saturates, so pushing to $B = 4{,}096$ slows training by 349% relative to the minimum at $B =$ 466.

The Playbook's rule of thumb implicitly assumes the first case: roughly flat step time below saturation ("no overhead from parallel computations") and saturation below critical batch size, leading to "use the largest batch size possible." Small image tasks can hit the second regime instead, though the Playbook's closing caution covers both: "There is no point in using a larger batch size if it ends up increasing the training time."

Epoch budgets, step budgets and cost

Every real batch-size study also fixes training length, either by total examples processed, called an epoch budget (or token budget $E_{\text{tok}} = B_{\text{tok}} S$ in sequence modeling), or by fixed optimizer steps $S$ (a step budget). Under McCandlish et al.'s curve, fixing examples favors small batches because $E(B)$ grows with $B$, whereas fixing steps favors large batches because $S(B)$ falls with $B$. As the Playbook warns: "Comparing batch sizes with an epoch budget only probes the perfect scaling regime, even when larger batch sizes might still provide a meaningful speedup by reducing the number of training steps required." On modern LLM runs parameterized in tokens per step $B_{\text{tok}}$, switching from fixed tokens ($E_{\text{tok}}$) to fixed updates ($S$) flips the bias in the same way.

The distinction also reframes published benchmarks. Goyal et al. [2] trained ImageNet ResNets for a fixed 90 epochs across batch sizes and observed error staying "stable across a broad range of minibatch sizes, from 64 to 8k, after which it begins to increase." As Shallue et al. emphasize, an epoch budget allows larger batches to match smaller ones only while scaling remains perfect, so 8k probably marks the end of perfect scaling on ImageNet rather than an inherent generalization defect.

Resource consumption

Wall-clock time is not the only budget spent. The Playbook distinguishes upfront engineering costs ("purchasing new hardware or rewriting the training pipeline" for distributed training) from usage costs like accelerator-hours and power. Usage obeys the same product law:

$$\text{consumption} = (\text{per step}) \times (\text{steps}).$$

Raising the batch size reduces step count, so total cost hinges on how resource use per step scales across the three hardware regimes sketched below.

Though the Playbook leaves this implicit, one corollary simplifies single-host tuning: when hardware is fixed, usage cost is measured in device-hours proportional to wall-clock time, so minimizing training time (Figure 6) simultaneously minimizes usage cost. Time and cost only diverge when larger batches add accelerators or move to costlier nodes.

Upfront distributed-systems work cuts two ways. Early on, the Playbook warns it "might be better to defer increasing the batch size until the project has matured" rather than debugging multi-host synchronization too soon, yet "a large speedup in training time might be beneficial early in the process when many tuning experiments are needed."

Changing the batch size means retuning

Every throughput gain above assumes you retune hyperparameters at each batch size. The Playbook states this bluntly: "The optimal values of most hyperparameters are sensitive to the batch size. Therefore, changing the batch size typically requires starting the tuning process all over again." That cost explains why getting batch size right early saves costly retuning later.

The learning rate illustrates the shift directly. In McCandlish et al.'s model, best SGD step size follows $\eta^{\star}(B) = \eta_{\max}/(1 + B_{\text{noise}}/B)$, rising linearly below noise scale before saturating at $\eta_{\max}$ (Figure 9). In practice scaling behavior varies by optimizer:

  • Linear scaling for momentum SGD. Goyal et al.'s heuristic multiplies $\eta$ by $k$ when batch size scales by $k$, supplemented with warmup early in training and breaking past 8k on ImageNet; Zhang et al. (2019) [9] confirmed linear scaling below critical batch size.
  • Between square root and linear for Adam. McCandlish et al. found optimal Adam and RMSProp learning rates obey $\varepsilon(B) \propto B^{\alpha}$ ($\alpha \in [0.5, 1.0]$) before flattening above noise scale.
  • No universal scaling law. Shallue et al. found optimal rates "did not always follow either a linear or square root scaling heuristic," reinforcing empirical re-sweeps (meanwhile, Maximal Update Parameterization, or $\mu$P [7], stabilizes optimal learning rates across model width scaling, solving a different dimension than batch scaling).

Because scaling formulas disagree across optimizers, I treat them purely as initial guesses to center a fresh learning-rate sweep rather than replacements for tuning.

Optimal regularization shifts too. The Playbook's FAQ notes smaller batches inject sampling noise that "can have a regularizing effect," making larger batches need stronger regularization. Both Hoffer et al. and Shallue et al. stay measured, attributing large-batch gaps mainly to update budgets and noting "other regularization techniques, such as label smoothing, can replace this effect."

Normalization: decoupling statistics or dropping batch dependence

Batch normalization [4] creates an extra coupling because its layer mean and variance depend directly on the batch examples. Goyal et al. explain that altering the statistics subset size $n$ "changes the underlying loss function L that is optimized," so they fixed $n = 32$ examples per worker.

The Playbook recommends that BatchNorm "should use a different batch size than the gradient computation to compute statistics." Ghost batch norm [3] splits a large gradient batch into smaller normalization chunks (e.g., 64 or 128), keeping the loss invariant across batch sweeps. Better still in new architectures, the Playbook notes BatchNorm "can often be replaced with LayerNorm"; modern Transformers and foundation models go a step further with RMSNorm [8], which preserves rescaling invariance without mean-recentering or any dependence on batch composition (Part 9 covers multi-device normalization details).

In practice

Putting the pieces together yields a concrete six-step procedure for picking batch size on a new workload. Steps 1 to 4 distill the Playbook's sections on throughput estimation ↗ and training-time optimization ↗, while Steps 5 and 6 cover retuning ↗ and resource consumption ↗.

  1. Measure throughput by doubling

    Benchmark short runs across powers of two (8, 16, 32, ...) until memory fails, logging examples or tokens per second throughout.

  2. Fix bottlenecks before choosing

    If throughput stalls below hardware saturation, diagnose data-loading or collective-communication limits before proceeding.

  3. Keep the batch sizes that raise throughput

    Discard sizes past the throughput plateau even when they fit in memory, and rely on gradient accumulation only to reach target optimization batch sizes across sharded replicas.

  4. Default to the largest of them

    Without extra experiments, select the largest batch still raising throughput. To verify directly, compare candidates under a fixed step budget after retuning each one.

  5. Retune whenever the batch size changes

    Re-sweep learning rate, momentum, and regularization, using scaling rules solely to center the grid. Keep BatchNorm statistics decoupled, or adopt LayerNorm or RMSNorm.

  6. Weigh cost only when hardware changes

    On fixed devices the fastest batch size minimizes device-hours too; weigh per-step cost against step savings only when adding nodes or upgrading accelerators.
