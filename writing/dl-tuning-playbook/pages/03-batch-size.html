Choosing the batch size

Josh Speagle Notes on the Playbook's section on choosing the batch size ↗

Part of a series of notes on Google Research's Deep Learning Tuning Playbook. Read what the Playbook is and how these notes work.

The batch size is one of the first settings we fix on a new project, and it is tempting to treat it like the learning rate: try a few values and keep whichever validates best. The Playbook argues against this for a simple reason: once the other hyperparameters are retuned and the run is long enough, the batch size changes how quickly we reach a result rather than how good that result can be, so the questions worth asking are about hardware, speed and cost. In this post I want to build that argument up piece by piece. We'll start with the evidence that batch size does not limit final performance, then split training time into the time each step takes and the number of steps needed, see how the two combine, and look at what budgets and costs do to a comparison. We'll finish with why every change of batch size forces a round of retuning.

What does the batch size actually control?

The Playbook's position fits in two sentences. The batch size "governs the training speed and shouldn't be used to directly tune the validation set performance", and "often, the ideal batch size will be the largest batch size supported by the available hardware" . The first claim carries a condition that is easy to skip past. Only if the learning rate, the regularization hyperparameters and the number of training steps are retuned for each batch size do Godbole et al. expect the same final performance from any batch size.

Most of the evidence comes from Shallue et al. , who retuned every run at every batch size across workloads spanning several model families, optimizers and datasets. Their abstract is carefully worded: "We find no evidence that larger batch sizes degrade out-of-sample performance." The Playbook's FAQ is equally careful, reporting "no convincing evidence that the batch size affects the maximum achievable validation performance". We should read both as the absence of an effect on the workloads tested, which is weaker than a proof that no such effect exists.

This can sound at odds with experience, since many of us have watched validation error get worse after raising the batch size. The Playbook agrees that "changing the batch size without changing any other details of the training pipeline will often affect the validation set performance", and the culprit is usually two settings that stay fixed by accident:

  • The number of epochs. A script that trains for a fixed number of epochs (passes over the training set) processes a fixed number of examples $E$, so the number of steps $S = E/B$ falls as the batch size $B$ grows, and each doubling of the batch halves the number of weight updates. Hoffer et al. found that the large-batch gap in their experiments "stems from the relatively small number of updates rather than the batch size", and they closed it by training for proportionally more updates with an adjusted learning rate.
  • The learning rate and regularization. A learning rate tuned at $B = 64$ is usually a poor choice at $B = 2{,}048$, because averaging more examples gives a less noisy gradient that can support larger steps (we'll see why when we get to steps needed). The Playbook singles out the optimizer hyperparameters (learning rate, momentum) and the regularization hyperparameters as the ones that interact most strongly with the batch size.

If the batch size mainly sets speed, then the reasons to care about it are practical ones. As the Playbook puts it, faster training lets us tune hyperparameters more thoroughly within a fixed amount of time, and it shortens the development cycle so that new ideas get tested more often. To reason about speed, I find it helpful to write training time as the product of step latency (seconds per step) and step count:

$$T(B) \;=\; \htmlClass{math-col-third}{t_{\text{step}}(B)} \times \htmlClass{math-col-fourth}{S(B)}.$$

The decomposition is useful because each factor depends on the batch size for a different reason: step latency is a property of the hardware, while step count is a property of the gradient's statistics. We'll take them one at a time.

Time per step on real hardware

Before we can say anything about speed on a new workload, we need to know which batch sizes fit on the accelerator (a GPU or TPU) at all, and how long a step takes at each. Two properties of the hardware decide this, memory and parallelism.

  • Memory sets an upper limit. During training the accelerator holds the weights, their gradients and the optimizer state (Adam keeps two extra values per weight), none of which depend on the batch size. It also holds the activations of every layer for every example in the batch, because the backward pass needs them to compute the gradient. Activation memory therefore grows in proportion to $B$, and above some batch size the run fails with an out-of-memory error. The Playbook calls accelerator memory "usually" the limiting factor, and warns that the limit "can be difficult to calculate ... without running, or at least compiling, the full training program".
  • Parallel hardware saturates. The accelerator processes the examples of a batch in parallel, so at small batch sizes some of its arithmetic units sit idle and a batch twice as large takes about the same time per step. Once the units are busy, a batch twice as large takes about twice as long. Training throughput (examples processed per second, $B / t_{\text{step}}$) therefore doubles with each doubling at first and then levels off at a throughput plateau. The Playbook states the first half of this directly: "When the accelerators aren't yet saturated, if the batch size doubles, the training throughput should also double (or at least nearly double)."

Since the memory limit is hard to predict, the Playbook's suggestion is to measure it empirically with a doubling procedure: train for a small number of steps at increasing powers of two until one run exceeds memory, recording the throughput of each run along the way. Two outcomes call for action:

  • Throughput does not double below saturation. This points to a bottleneck in the pipeline, "such as I/O or synchronization between compute nodes", which the authors say "may be worth diagnosing and correcting before proceeding".
  • Throughput stops rising. Here the advice is to consider only batch sizes up to that point, "even if a larger batch size is supported by the hardware", because "all benefits of using a larger batch size assume the training throughput increases".

On the saturating accelerator, every doubling up to $B =$ 1,024 raised throughput by at least 14%, while the next doubling added only 1%, so the procedure stops there. The preset tells a different story: throughput stalls near 2,000 examples per second from $B =$ 256 onward, well below the accelerator's peak. An early plateau like this is what we would expect from a data loader that cannot keep the accelerator busy.

What about batch sizes beyond the memory limit? Gradient accumulation appears to offer a way past it, by summing the gradients of several micro-batches before updating the weights once. The Playbook advises against it in applied work, because it "simulates a larger batch size than the hardware can support and therefore does not provide any throughput benefits". The micro-batches run one after another, so the time per step grows in proportion to the accumulated batch size. Finally, the authors point out that these measurements "may need to be repeated every time the model or optimizer is changed", since a different architecture can change what fits in memory.

Steps needed fall, then level off

The second factor is the number of steps needed to reach a fixed validation goal, again with the hyperparameters retuned at each batch size. Shallue et al. measured this "steps to result" on every workload in their study and found the same three-part shape each time: "an initial period of perfect scaling ... where the steps needed to achieve the error goal halves for each doubling of the batch size", then "a region of diminishing returns", and finally "a region of maximal data parallelism where additional parallelism provides no benefit whatsoever". They "never saw the number of steps to reach a goal validation error increase when the batch size was increased". The Playbook adopts the halving regime under the name perfect scaling and states the last observation as a rule (more steps are "never" needed), although we should remember that it is an empirical regularity rather than a theorem.

Why should the curve have this shape? The answer lies in gradient noise. Each step uses an estimate of the full-data gradient computed from $B$ examples, and the error of that estimate has a variance proportional to $1/B$, because averaging $B$ independent per-example gradients divides their variance by $B$. While noise dominates, the optimizer is forced to take small steps, so one step at double the batch size is nearly as good as two steps at the smaller one. Once the estimate is accurate, though, adding more examples barely improves it, and the curvature of the loss becomes what limits the step size. McCandlish et al. turned this intuition into a quantitative model, which is what we'll use for the rest of the post.

If we turn progress per step into a step count, we arrive at McCandlish et al.'s model of the steps $S$ and training examples $E$ needed to reach a goal at batch size $B$ (their Eq. 2.11, solved at fixed $B$):

$$\begin{aligned} \htmlClass{math-col-fourth}{S(B)} &= S_{\min}\left(1 + \frac{\htmlClass{math-col-model}{B_{\text{crit}}}}{B}\right), \\[4pt] E(B) = B\,S(B) &= E_{\min}\left(1 + \frac{B}{\htmlClass{math-col-model}{B_{\text{crit}}}}\right). \end{aligned}$$

Here $S_{\min}$ is the number of steps a very large batch needs, $E_{\min}$ is the number of examples a very small batch needs, and their ratio $B_{\text{crit}} = E_{\min}/S_{\min}$ is the critical batch size. The two equations make the trade-off explicit: raising $B$ always lowers the step count, but it always raises the number of examples processed. McCandlish et al. fit $B_{\text{crit}}$ to measured runs, and their noise argument predicts it to be close to the gradient noise scale averaged over training. At $B = B_{\text{crit}}$ a run takes twice the minimum number of steps and twice the minimum number of examples, a point they describe as "a natural compromise between time and compute".

Where the noise scale comes from

The derivation is short enough to sketch. Let $G$ be the full-data gradient, $H$ the Hessian (the matrix of second derivatives of the loss), and $\Sigma$ the covariance of a single example's gradient. A step of size $\eta$ along a mini-batch estimate changes the loss, to second order and on average, by

$$\Delta L(\eta) \approx -\eta\,|G|^2 + \tfrac{1}{2}\,\eta^2\left(G^{\top} H G + \frac{\operatorname{tr}(H\Sigma)}{B}\right).$$

Minimizing over $\eta$ gives McCandlish et al.'s Eqs. 2.6 and 2.7:

$$\eta^{\star}(B) = \frac{\eta_{\max}}{1 + B_{\text{noise}}/B},$$ $$\Delta L^{\star}(B) = \frac{\Delta L_{\max}}{1 + B_{\text{noise}}/B},$$

where $\eta_{\max} = |G|^2 / G^{\top} H G$ is the best step on the exact gradient and $B_{\text{noise}} = \operatorname{tr}(H\Sigma)/G^{\top} H G$ is the noise scale (their Eq. 2.8). If the Hessian is close to a multiple of the identity, this reduces to $B_{\text{simple}} = \operatorname{tr}(\Sigma)/|G|^2$ (their Eq. 2.9), which can be estimated during training. We should keep the limits of the argument in mind: it is local to one step, it assumes a tuned learning rate, and, as the authors note themselves, it "says nothing about generalization".

One source of confusion when reading this literature is that different papers attach the phrase "critical batch size" to different points on the same curve, as shows. The tolerances below are my own algebra on McCandlish et al.'s curve rather than anything the papers compute:

  • The Playbook uses the phrase for the end of perfect scaling: "Perfect scaling holds for all batch sizes up to a critical batch size, beyond which one achieves diminishing returns." On a smooth curve, though, that end can only be located with a tolerance. Zhang et al. (2024) choose one, defining the critical batch size as the point where the steps needed exceed perfect scaling by 20%. On McCandlish et al.'s curve that point is $B_{\text{crit}}/5$, because the ratio of $S(B)$ to the perfect-scaling line $S_{\min} B_{\text{crit}}/B$ is $1 + B/B_{\text{crit}}$.
  • McCandlish et al. place $B_{\text{crit}}$ in the middle of the bend, where a doubling saves 25% of the steps.
  • Shallue et al. call the point where steps stop falling the "maximum useful batch size". If we take "stop" to mean within 10% of the floor $S_{\min}$, it lies at $10\,B_{\text{crit}}$.

To keep things unambiguous, I'll use $B_{\text{crit}}$ in McCandlish et al.'s sense for the rest of this post, because it comes with an equation, along with $B_{\text{noise}}$ for the single-step gradient noise scale, $B_{\text{sat}}$ for the hardware saturation batch size, and "end of perfect scaling" for the Playbook's point.

Whichever definition we use, the critical batch size is not a universal constant: it depends on both the workload and the goal. The Playbook says the time-minimizing batch size "depends on the dataset, model, and optimizer", and calls it "an open problem how to calculate it other than finding it experimentally for every new problem". The literature bears this out. McCandlish et al. found that the critical batch size "typically increases by an order of magnitude or more over the course of training", which means a harder goal has a larger one, and across tasks their values ranged from about 20 for a small autoencoder to over 10 million for a Dota 2 agent. Zhang et al. (2019) found that momentum and preconditioned optimizers such as Adam raise it, while for language-model pre-training Zhang et al. (2024) found that it grows mainly with the amount of training data (roughly as $D^{0.47}$) and only weakly with model size at fixed data.

Wall-clock time is the product of the two

We now have both factors, so we can put them back together as $T(B) = t_{\text{step}}(B) \times S(B)$. The cleanest way to see what happens is on log axes, where a product becomes a sum and the curve of $\log T$ is simply the vertical sum of the curves of $\log t_{\text{step}}$ and $\log S$. Below saturation the time per step is flat, so training time falls exactly as fast as the step count. Above saturation the time per step doubles with each doubling of $B$, while the step count at best halves, which means training time can at best stay level. The fastest batch size therefore sits near the saturation batch size or the end of perfect scaling, whichever comes first.

What matters most is the order in which these two limits arrive, and the presets show both possibilities:

  • Perfect scaling ends well past saturation (, ending at 16,384). Here step latency and step count cancel over a wide range, and every batch size from 704 to 5,953 (a range of 8.5×) finishes within 5% of the fastest time, so any batch size that saturates the accelerator is close to optimal.
  • Perfect scaling ends before saturation (, ending at 64, so $B_{\text{crit}} =$ 320). Now the step count flattens while the time per step is still constant, and batches above saturation actively slow training down. The minimum is at $B =$ 466, and $B = 4{,}096$ takes 349% longer.

The Playbook's rule of thumb implicitly assumes we are in the first case. It treats the time per step as roughly constant across feasible batch sizes, which holds "when there is no overhead from parallel computations and all training bottlenecks have been diagnosed and corrected", and then observes that "often, the largest batch size supported by the available hardware will be smaller than the critical batch size". From these two premises it concludes that "a good rule of thumb (without running any experiments) is to use the largest batch size possible". The second case is the exception, but it is not hypothetical, since McCandlish et al. measured critical batch sizes in the hundreds for small image tasks. Fortunately the Playbook's closing point covers both: "There is no point in using a larger batch size if it ends up increasing the training time."

Epoch budgets, step budgets and cost

So far we have assumed that each run trains for as long as it needs. A real comparison of batch sizes has to fix a training length for each run, and we can fix it either in examples (an epoch budget) or in steps (a step budget). This choice, which can look like bookkeeping, quietly decides which batch size looks best. Under McCandlish et al.'s model the examples needed, $E(B)$, grow with the batch size while the steps needed, $S(B)$, shrink. A fixed epoch budget therefore favors small batches, which use examples efficiently, whereas a fixed step budget favors large batches, which use steps efficiently. This is the reasoning behind the Playbook's warning that "Comparing batch sizes with an epoch budget only probes the perfect scaling regime, even when larger batch sizes might still provide a meaningful speedup by reducing the number of training steps required."

The distinction also changes how we should read published comparisons. Goyal et al. trained ImageNet ResNets for a fixed 90 epochs at every batch size and found error "stable across a broad range of minibatch sizes, from 64 to 8k, after which it begins to increase". Shallue et al. point out that under an epoch budget a larger batch can match a smaller one only while scaling is perfect. My reading, then, is that the 8k limit may mark the end of perfect scaling for that workload rather than a point where large batches start to generalize worse.

Resource consumption

Time is not the only thing a batch size spends, so the Playbook also considers cost. It separates the costs of a larger batch into upfront costs, "e.g. purchasing new hardware or rewriting the training pipeline to implement multi-GPU / multi-TPU training", and usage costs such as cloud bills, team compute budgets and electricity. Usage decomposes into the same kind of product we wrote for time:

$$\text{consumption} = (\text{per step}) \times (\text{steps}).$$

A larger batch always reduces the number of steps, so the outcome hinges on what happens to the consumption per step, and the Playbook gives an example of each of the three possibilities.

The Playbook doesn't spell this out, but I think one consequence simplifies matters considerably. On a fixed set of accelerators, usage is measured in device-hours, which are proportional to wall-clock time, so on that hardware the batch size that minimizes training time also minimizes cost and answers both questions at once. The two goals only come apart when a larger batch requires more devices or different ones.

Upfront costs pull in two directions. On one hand, the Playbook suggests it "might be better to defer increasing the batch size until the project has matured", since multi-host pipelines can introduce bugs. On the other, "a large speedup in training time might be very beneficial early in the process when a lot of tuning experiments are needed".

Changing the batch size means retuning

Everything so far has assumed that each batch size gets its own tuned hyperparameters, and that assumption has a price. The Playbook is blunt about it: "The optimal values of most hyperparameters are sensitive to the batch size. Therefore, changing the batch size typically requires starting the tuning process all over again." This is why the authors recommend thinking carefully about the batch size at the start of a project, because retuning everything later "might be difficult, time consuming, and expensive".

The learning rate is the clearest illustration. In McCandlish et al.'s model the best SGD learning rate is $\eta^{\star}(B) = \eta_{\max}/(1 + B_{\text{noise}}/B)$ (their Eq. 2.6), which grows in proportion to $B$ well below the noise scale and levels off at $\eta_{\max}$ well above it, as we can see in . Empirically, though, the right way to scale the learning rate depends on the optimizer:

  • Linear scaling for momentum SGD. Goyal et al.'s rule is "When the minibatch size is multiplied by k, multiply the learning rate by k." They report that it breaks down early in training, which they handle with warmup, and beyond a batch size of about 8k on ImageNet. Zhang et al. (2019) found the optimal learning rate of SGD "scales linearly with batch size before it hits the critical batch size".
  • Between square root and linear for Adam. McCandlish et al. found that "for Adam and RMSProp the optimal learning rate initially obeys a power law $\varepsilon(B) \propto B^{\alpha}$ with $\alpha$ between 0.5 and 1.0 depending on the task, then becomes roughly constant" (their $\varepsilon$ is the learning rate and their $\alpha$ an exponent).
  • No reliable rule. Shallue et al. found that the optimal values "did not always follow either a linear or square root scaling heuristic".

Given this disagreement, I think the safest way to use a scaling rule is as a good place to center the new search, which we still have to run.

The optimal regularization moves too. The Playbook's FAQ argues that smaller batches add sampling noise that "can have a regularizing effect", so larger batches "may require stronger regularization and/or additional regularization techniques". The papers we've been following are more cautious on this point: Hoffer et al. attribute the large-batch gap to the number of updates rather than to lost noise, and Shallue et al., while granting that small-batch noise may regularize, note that "other regularization techniques, such as label smoothing, can replace this effect".

Batch norm couples the batch size to the model

There is one case where the batch size does more than change the optimization, because it changes the model itself. Batch normalization normalizes each layer's activations with a mean and variance computed over the examples in the batch, so in a model that uses it the batch size enters the forward computation. Goyal et al. make the consequence explicit: changing the number of examples $n$ used for these statistics "changes the underlying loss function L that is optimized", because the statistics "computed by BN with different n exhibit different levels of random variation". Their solution was to fix $n = 32$ examples per worker.

The Playbook generalizes this into the advice that batch norm "should use a different batch size than the gradient computation to compute statistics". Ghost batch norm, introduced by Hoffer et al., does exactly this by normalizing small virtual batches inside a large one (they used ghost batches of 128). The Playbook adds anecdotal reports that statistics over about 64 examples work better in practice, and points out that separating the two sizes "is particularly useful for batch size comparisons", since the loss being compared then stays fixed. Alternatively, batch norm "can often be replaced with LayerNorm", which does not depend on the batch at all. We'll return to the implementation details for multiple devices in Part 9.

In practice

Putting the pieces together, the Playbook's advice on batch size condenses into a short procedure you can follow on a new workload. Steps 1 to 4 come from its sections on feasible batch sizes and throughput ↗ and on minimizing training time ↗. Steps 5 and 6 come from its sections on retuning ↗ and resource consumption ↗.

  1. Measure throughput by doubling

    Run a few steps at batch sizes 8, 16, 32, and so on until a run fails for memory, recording examples per second for each.

  2. Fix bottlenecks before choosing

    If throughput does not nearly double while the accelerator is unsaturated, look for an input or synchronization bottleneck first.

  3. Keep the batch sizes that raise throughput

    Drop batch sizes past the throughput plateau, even if they fit, and avoid gradient accumulation, which adds no throughput.

  4. Default to the largest of them

    Without further experiments, use the largest batch size that still raises throughput. If you want to check it, compare candidates by steps to a fixed goal under a step budget, retuning at each batch size.

  5. Retune whenever the batch size changes

    Retune the learning rate, momentum and regularization, using a scaling rule only to center the search. With batch norm, keep the statistics size fixed.

  6. Weigh cost only when hardware changes

    On fixed hardware the fastest batch size is also the cheapest. Only when a larger batch needs more or better devices do you need to weigh consumption per step against the steps saved.

Where this fits

The batch size belongs with the architecture, the optimizer and the initial configuration as one of the decisions we make once at the start of a project, which is exactly why getting it right matters given the cost of retuning later.
